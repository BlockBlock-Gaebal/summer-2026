# 🎬 데모 실행절차 — 시나리오 실행·검증 (오라클·데모 파트)

> 담당: 유안(오라클·데모). `scripts/seed.ts` · `scripts/submit.ts` 기준.
> **이 문서는 데모 시나리오를 어떤 명령으로 실행하고 그 결과를 어떻게 검증하는지**를 다룬다.
> 최신 확정 수치는 여기와 `docs/DECISIONS.md`를 본다.

---

## 0. 전제 — 방 생성·참여는 사전 세팅한다 (D-18)

방 생성·참가자 등록은 **실행 전에 미리 끝내둔다.** 실행 시점에는 `submit.ts`만 누른다.
근거: 다수 지갑 서명은 실패 리스크가 크고, 부수 효과로 "빈 방에 `submit_results` 호출 →
전멸 오판정" 사고(D-22)도 원천 차단된다.

**사전 세팅 (방 1개당 1회):**

```bash
cd scripts
npm run seed        # A(유안=오라클) 자동 join. B/C 주소가 .env에 있으면 안내 커맨드 출력
```

B/C는 `seed.ts`가 대신 서명해주지 않는다 (각자 실제 서명 주소가 필요 — 회의 결정,
CLAUDE.md §5-1 "돈은 온체인, 인증은 오프체인"과 별개로 join 자체는 각자 서명 필수).
`seed.ts` 출력에 찍히는 `sui client ptb ...` 명령을 B/C 계정으로 직접 실행해 참여를
완료해둔다. `npm run read-state -- <방ID>`로 **참가자 3명, 상태 PENDING**을 확인하면
사전 세팅이 끝난 것이다.

## 1. 시나리오 (고정값 — `submit.ts`의 `SCHEDULE`와 반드시 일치)

D = 5, α = 0.2, 3인 균등 예치.

| day | 사건 | 근거 |
|---|---|---|
| 1 | B 탈락 | — |
| 2 | 없음 | — |
| 3 | C 탈락 | — |
| 4 | 없음 | — |
| 5 | A 완주 (submit 5회 후 자동 finalize) | `submit.ts`가 5일째 제출 직후 `finalize()`까지 자동 호출 |

아래 표는 2026-08-15에 데모 방(`DEPLOYMENT.md` 방③, `0x2f6f1b32...`)에서 이 시나리오
그대로 5일 + finalize까지 실제로 돌려서 나온 **테스트넷 실측값(MIST 원단위)**이다
(stake는 검증용 20,000,000 MIST = 0.02 SUI). 진모가 파이썬 미러로 별도 계산해
**완전히 일치함을 확인했다** — 이 값이 정본이다.

| | 예치 (stake) | failed_day | 커브 환급 | 생존 배당 | **최종 수령 (claimable)** |
|---|---|---|---|---|---|
| A | 20,000,000 | 0 (완주) | 20,000,000 (원금 전액) | 31,840,000 | **51,840,000** |
| B | 20,000,000 | 1 | 0 | 0 | **0** |
| C | 20,000,000 | 3 | 4,160,000 | 4,000,000 | **8,160,000** |
| 합계 | 60,000,000 | | | | **60,000,000** (dust 0) |

**합계 60,000,000 = 예치 60,000,000, dust 0.** 커브 환급·생존 배당 열은 최종 수령을
분해해 본 것이고, 체인에서 직접 읽히는 값은 `stake` · `failed_day` · `claimable` 세
가지다 (`npm run read-state -- <방ID>` 출력과 그대로 대조된다). 대조 검증기는
`docs/정산_프로토타입/03_시뮬레이터/verify_onchain.py`, 결정 기록은 `DECISIONS.md` §10.2(D-27).

**C의 분해가 검증의 핵심이다.** C는 중간에 탈락했는데도 8,160,000을 받는다. 그중
4,000,000은 살아있던 day1~3 동안 B의 몰수분에서 흘러들어온 배당이다 — "탈락해도
버틴 기간의 몫은 가져간다"는 설계 성질이 숫자로 확인되는 지점이다. 반면 B는 day1
탈락이라 완주일수 k=0 → 환급 0 → 배당도 0 → 전액 몰수. 같은 "탈락"인데 시점에 따라
결과가 완전히 갈린다.

## 2. 실행 순서

사전 세팅이 끝난 방(참가자 3명, PENDING)에서 시작한다.

| 순서 | 명령 | 결과 |
|---|---|---|
| 1 | (사전) `npm run seed` + B/C 각자 `sui client ptb` join | 참가자 3명, 상태 PENDING |
| 2 | `npm run submit` | day1 진행 — B 탈락, 환급 0 |
| 3 | `npm run submit` | day2 진행 — 탈락자 없음 (빈 명단으로도 반드시 호출해야 진행된다) |
| 4 | `npm run submit` | day3 진행 — C 탈락 |
| 5 | `npm run submit` ×2 | day4·day5 진행. 5번째 호출에서 `finalize()` 자동 실행 |
| 6 | `npm run read-state -- <방ID>` | 상태 ENDED, 참가자별 stake / failed_day / claimable, vault 확인 |

`submit.ts`는 체인의 `current_day`를 직접 읽어 다음 날짜를 스스로 판단한다. 몇 번에
나눠 누르든 **순서만 맞으면** 안전하다.

대시보드는 5초 폴링이라 `submit` 후 자동으로 값이 따라온다. 안 뜨면
`npm run read-state -- <방ID>`가 동일한 정보(참가자별 stake/failed_day/claimable,
vault, status)를 터미널에서 사람이 읽기 좋은 표로 출력한다 (D-16 백업 경로).

## 3. 방 ID 주의사항

- ⚠️ **방③(`0x2f6f1b32…`)에는 다시 `submit`하지 마라.** §1 실측값이 나온 검증 기준점이라
  상태를 그대로 보존해야 한다 (D-27). 리허설은 방④(`0xe11d8984…`)로 한다
- ⚠️ **빈 방에 `submit_results`를 호출하지 마라.** 참가자 0명이면 생존자 지분합이 0이라
  전멸로 판정돼 `status`가 즉시 ENDED로 잠기고 되돌릴 수 없다. 가드는 미도입 확정(D-22)이라
  운용 규칙으로만 막는다. 기존 배포 방 `0xfb1eb0…`이 실제로 빈 방이다 — 이 ID로 submit하면
  그대로 터진다. `read_state.ts`가 빈 방을 감지하면 경고를 출력한다
- 방 ID의 정본은 `docs/DEPLOYMENT.md`다 (D-20)
- `submit.ts`는 `ORACLE_PRIVATE_KEY`가 있는 기기에서만 실행된다. `scripts/.env`는 gitignore
  대상이라 클론만으로는 안 딸려온다 — 새 기기에서 돌릴 때 먼저 확인할 것

## 5. 재현 방법

새 방에서 처음부터 다시 돌리려면 `npm run seed` → B/C join → `npm run submit` ×5다.
시나리오가 `submit.ts`의 `SCHEDULE`에 고정돼 있어 **매번 같은 시나리오·같은 결과**가 나온다.
결과가 §1 표와 어긋나면 `verify_onchain.py` 상단 시나리오 블록을 새 방 기준으로 고쳐
미러와 대조한다.
