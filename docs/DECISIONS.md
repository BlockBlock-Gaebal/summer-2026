## 3. D-05 적용 후 커브 (α = 0.2, D = 5, stake 10 SUI)

| 입력 | 상황 | 환급 (MIST) | SUI | 하루 더 버틴 값 |
|---|---|---|---|---|
| k = 0 | day1 탈락 | 0 | 0.00 | — |
| k = 1 | day2 탈락 | 720,000,000 | 0.72 | +0.72 |
| k = 2 | day3 탈락 | 2,080,000,000 | 2.08 | +1.36 |
| k = 3 | day4 탈락 | 4,080,000,000 | 4.08 | +2.00 |
| k = 4 | day5 탈락 | 6,720,000,000 | 6.72 | +2.64 |
| k = 5 | 완주 | 10,000,000,000 | 10.00 | **+3.28** |

전 구간 MIST 정수로 정확히 떨어진다 (분자 `10000k + 8000k²`, 분모 250000).
생존 임금이 전 구간 단조증가하며, 구 인덱싱에 있던 마지막 날 절벽(`… 2.56, 3.12, 0`)이 사라진다.

**부수 성질.** α = 1(순수 선형)일 때 몰수액은 `s(D−k)/D`, 스트림 길이는 `D−d+1 = D−k`이므로

```
일일 drip 증가분 = [s(D−k)/D] / (D−k) = s/D     (탈락 시점과 무관한 상수)
```

탈락 시점에 관계없이 방출량 증가분이 정확히 `stake/D`로 일정하다. **새 인덱싱에서만 성립하며**, T1 시나리오의 dust = 0이 우연이 아니라 구조적으로 보장된다는 뜻이다.

- **완료 (발표)** — 발표까지 끝났다. **여름 프로젝트는 종료 상태다.** 저장소 안에서 만들거나 검증할 것은 없다
- **남은 것** — 저장소 안에는 없다. 다음 작업은 블록톤 확장이며 첫 결정 항목은 **§13**에 미결로 정리해 뒀다
- **블로커** — 없음. 빈 방 가드는 **미도입으로 종결**(D-22)
- **해소** — `@mysten/sui` 메이저 버전 분기는 **1.x 통일로 종결**(D-26). `frontend`가 `^1.45.2`로 내려왔다
- **주의** — JSON-RPC 폐지로 `SuiClient`는 전부 실패한다. 승준·유안 모두 `SuiGrpcClient`를 써야 한다 (D-23)

## 8. 8/9 인터페이스 프리즈 회의 상세 (D-15 ~ D-21)

### 8.1 D-15. 인터페이스 프리즈 선언 및 그 범위

프리즈는 "코드 동결"이 아니라 **"남이 의존하는 부분을 말없이 바꾸지 않는다"**는 약속이다.

**프리즈 대상** (변경하려면 3인 합의 필요)

| 대상 | 이유 |
|---|---|
| public 함수 이름 · 인자 순서 · 타입 | 오라클 스크립트가 직접 호출 |
| 이벤트 필드 이름 · 타입 | 외부에서 참조 가능 |
| struct 필드 이름 · 타입 (`stake`, `failed_day`, `claimable` 등) | 대시보드가 이 이름으로 값을 읽음 |
| 함수 호출 순서 규약 | 데모 시나리오가 여기 묶임 |

**프리즈 비대상** (각자 재량)

| 대상 | 이유 |
|---|---|
| 배포 ID (Package / Challenge / Table / 오라클) | 이름이 아니라 주소. `DEPLOYMENT.md` 갱신 + 통보로 끝 |
| `total_days`, 예치금 등 파라미터 **값** | 값이 바뀌어도 인터페이스는 동일 |
| 함수 내부 구현 (assert 추가, 계산 정리 등) | 외부에서 관측되지 않음 |
| UI 디자인, 스크립트 내부 구조 | 남이 의존하지 않음 |

**변경이 필요할 때의 절차**

1. 혼자 고치고 나중에 통보하는 것 **금지**
2. 단톡에 먼저 제안 + 영향받는 파트 명시
3. 3인 확인 후 변경
4. 변경 완료 통보

근거: 3인이 비동기로 작업하는 구조에서, 인터페이스 변경은 변경자에게는 5분이지만 나머지 둘에게는 원인 불명의 몇 시간이 된다. 되돌리는 비용이 타인에게 전가되는 지점만 합의 대상으로 둔다.

### 8.2 D-16. 대시보드를 1순위 산출물로 확정

대시보드는 필수 산출물이며 최우선 순위다. 동시에 CLI 실연 경로도 제거하지 않고 유지한다.

- CLI 실연은 별도로 만드는 것이 아니라, 오라클 스크립트를 만들면 자동으로 확보되는 것이다 (추가 비용 0)
- 목적: 데모 실행 중 RPC 지연·지갑 문제 등 사고 시 전환 가능한 경로 확보
- 이는 스코프 축소가 아니라 **백업 경로 유지**다

**대시보드 구현 우선순위**

| 순위 | 항목 | 완료 정의 |
|---|---|---|
| 1 | RPC 연결 | Challenge 오브젝트가 콘솔에 찍힘 |
| 2 | ID config 분리 | 코드에 ID 하드코딩 0건 |
| 3 | **참가자 목록 표 렌더** | 주소/예치금/상태가 표에 표시 ← **최소 성립선** |
| 4 | 방 정보 표시 | `current_day`, vault, status 표시 |
| 5 | claimable + 탈락일 표시 | day1 탈락자가 0원으로 표시됨 |
| 6 | 새로고침 / 폴링 | submit 후 화면 값이 갱신됨 |
| 7 | 디자인 | — |

### 8.3 D-17. 대시보드는 읽기 전용 — 지갑 서명 트랜잭션 미구현

대시보드에서 join / claim 등 트랜잭션 전송 기능은 구현하지 않는다.

- D-09("읽기 전용 대시보드")의 재확인 및 명시적 범위 확정
- 상태 변경은 전부 오라클 스크립트(CLI)로 수행
- 근거: 지갑 서명 플로우는 초심자 기준 소요 시간 예측이 어렵고, 데모 흐름을 끊는 요소이며, 프로젝트 차별점(시간가중 차등 몰수) 증명에 기여하지 않는다

### 8.4 D-18. 데모는 방 생성·참여를 사전 세팅한 상태에서 시작

데모 실행 중에는 `create_challenge` / `join`을 실행하지 않는다. 방 생성과 참가자 등록을 사전에 완료한 상태에서 데모를 시작한다.

- 실행 중 지갑 다수 서명은 실패 리스크가 크고 시간을 잠식함
- 부수 효과: **참가자 0명 상태에서 `submit_results` 호출 시 전멸로 오인되어 즉시 ENDED되는 상황이 원천 차단됨**
- 운용 규칙: **빈 방에 `submit_results`를 호출하지 않는다.** 방 생성 후 참가자를 채운 뒤 진행 (오라클 온보딩 문서에 명시)

### 8.5 D-19. 표시용 계산은 프론트엔드, 금액 계산만 온체인

환급률(%), 완주일수 등 표시 목적의 파생값은 프론트엔드에서 계산한다. 이를 위해 컨트랙트에 뷰 함수를 추가하지 않는다.

- 커브 수식(`k = d-1`, `r(d) = α·(d/D) + (1−α)·(d/D)²`, α=0.2)은 확정 상태이므로 프론트에서 계산해도 온체인 값과 일치
- **원칙**: 돈이 실제로 움직이는 계산만 온체인, 화면에 보여주기 위한 계산은 프론트
- 근거: 표시 편의를 위한 컨트랙트 수정은 재배포를 유발하며, 이는 크리티컬 패스(대시보드)에 불필요한 잡음을 넣는다

### 8.6 D-20. 배포 정보의 정본 위치

배포 ID 4종의 정본은 `docs/DEPLOYMENT.md` 한 곳으로 한다.

- 재배포 시 절차: ① `DEPLOYMENT.md` 갱신 → ② PR → ③ 단톡 통보
- 각자 코드에서는 config 파일/환경변수 한 군데로 모아 참조 (파일명·형식은 각자 재량)
- 카톡·개인 메모의 ID는 사본이며, 불일치 시 이 파일이 우선

### 8.7 D-21. 참가자 Table 조회 로직은 공용 스크립트로 제공

`Table` dynamic field 조회 로직을 `scripts/read_state.ts`로 공용화하며, 작성 책임은 **진모(컨트랙트 담당)**가 진다.

- `Table`은 dynamic field로 저장되어 `getObject`로 내용 조회 불가 → 2단계 조회 필요
- 이는 프론트엔드 구현 난이도 문제가 아니라 **컨트랙트의 저장 구조에서 파생된 문제**이므로 컨트랙트 담당이 해소한다
- 프론트엔드(승준)와 오라클(유안) 양쪽에서 재사용
- **2026-08-10 완료.** 조회 로직은 export, CLI 실행부는 분리 — 대시보드는 `import { readState }`로 가져다 쓰고 출력만 자기 방식으로 하면 된다

## 9. 8/10 구현 중 확정 (D-22 ~ D-24)

> 회의가 아니라 `scripts/` 착수 과정에서 실측으로 드러난 사항들이다. 셋 다 외부 환경 변화가 원인이다.

### 9.1 D-22. 빈 방 `submit_results` 가드 — 미도입 확정

참가자 0명인 방에 `submit_results`를 호출하면 생존자 지분합이 0이라 전멸로 판정되어
`status`가 즉시 `ENDED`로 잠긴다 (`challenge.move:245`). 되돌릴 수 없다.
가드를 넣을지 8/9 회의에서 보류했고, **넣지 않는 것으로 종결**한다.

- **재배포 비용이 예상보다 크다.** `Published.toml`을 커밋한 뒤로 `sui client publish`가
  `Your package is already published. You have to manually remove the publication entry`로 거부한다
  (실측). `[published.testnet]` 항목 삭제 → publish → 새 값 재커밋 절차가 붙는다.
  `sui client upgrade`로 UpgradeCap을 쓰는 길도 있으나 어느 쪽이든 크리티컬 패스에 잡음이다
- 로컬 CLI 프로토콜 버전(129)이 testnet(132)보다 낮아 재배포 시 의존성 검증 오류 위험이 있다
- 데모는 사전 세팅으로 시작하므로(D-18) 실행 중 발생 경로가 없다
- **대체 방어**: ① 운용 규칙 "빈 방에 submit 금지" ② `read_state.ts`가 빈 방을 감지하면 경고를 출력
- ⚠️ 단, 기존 배포 방 `0xfb1eb0…`이 실제로 빈 방이다. **개발 중 리허설에서 이 ID로 submit하면 그대로 터진다.** 검증용 방(§DEPLOYMENT.md)을 쓸 것

### 9.2 D-23. 체인 접근은 gRPC로

공개 풀노드의 JSON-RPC가 폐지되었다. `@mysten/sui`의 `SuiClient`로 testnet을 치면
`getObject` / `getDynamicFields` / `getCoins` / `getBalance` 등 **시도한 7개 메서드가 전부**
`MethodNotFound: JSON-RPC on public fullnodes has been deprecated`로 실패한다 (실측).

- 대안은 `SuiGrpcClient`(gRPC-web). 실측으로 정상 동작 확인
- **D-11의 결정(직접 폴링, 인덱싱 미채택)은 그대로다.** 수단만 JSON-RPC → gRPC로 바뀐다
- 인터페이스 프리즈(D-15) 대상이 아니다 — 컨트랙트 시그니처는 불변, 클라이언트 접근 방식만 변경
- 함정 2개는 `frontend/README.md`·`scripts/README.md`·`read_state.ts` 상단에 명시했다
  (생성자 옵션은 `url`이 아니라 `baseUrl` / `core.getObject()` 대신 `ledgerService` + readMask `json`)

### 9.3 D-24. 데모 자금 조달과 코인 분할

**testnet faucet CLI가 폐지되었다.** `sui client faucet`은 Web UI 안내만 출력하고 종료한다(exit 1).
캡차가 필요해 스크립트로 자동화할 수 없다.

- "리허설마다 새 주소를 만들고 faucet으로 채운다"는 흐름은 **성립하지 않는다.** 폐기
- **고정 주소를 재사용한다.** 검증용 참가자 주소 2개(`verify-b`, `verify-c`)를 만들어 두었고
  충전은 이미 SUI를 가진 주소에서 `pay-sui`로 분배한다 (한 트랜잭션으로 다수 주소 동시 가능)
- **코인 분할은 PTB로 한다.** 회의에서 정한 "faucet 복수 수령으로 코인 오브젝트를 늘린다"는 대책은
  faucet 폐지로 무효다. 대신 PTB에서 가스 코인을 직접 쪼개면 **코인 오브젝트가 1개여도 동작한다**:

  ```bash
  sui client ptb \
    --split-coins gas "[100000000]" \
    --assign stake \
    --move-call <PKG>::challenge::join @<CHALLENGE> stake.0 \
    --gas-budget 30000000
  ```

  `sui client split-coin`이 실패하던 원인(쪼갤 코인 = 가스 코인)이 구조적으로 사라진다.
  실제로 코인 1개만 가진 주소 2개가 이 방식으로 join에 성공했다
- 유안의 `seed.ts`는 이 패턴 기준으로 재설계한다

## 10. 8/15~8/17 검증 중 확정 (D-26 ~ D-28)

### 10.1 D-26. `@mysten/sui` 버전 통일 — 1.x 기준으로 확정 (08-17)

**`scripts`는 `^1.30.0`, `frontend`는 `^2.24.0`으로 메이저 버전이 갈려 있었다** (실측).

### 10.3 D-28. α = 0.2의 근거 확립 — "직관 기반" 표기 제거

D-06에서 α=0.2를 확정했으나 §4에는 "현재 0.2는 직관 기반"이라고 적혀 있었다.
"왜 하필 0.2냐"에 답할 근거를 정리한 결과, **직관이 아니었음**이 드러났다.

**(1) 애초에 최적화로 구할 수 있는 값이 아니다.** 생존 임금
`w(d) = stake·[α/D + (1−α)(2d−1)/D²]`를 전개하면 마지막날/첫날 배율이 닫힌 형태로 떨어진다.

```
w(D)/w(1) = (2D−1−(D−1)α) / (1+(D−1)α)
```

α에 대한 **쌍곡선 감소라 극값이 없다.** "수학적으로 최적인 α"는 존재하지 않는다는 뜻이고,
따라서 α는 **목표 배율 T를 먼저 정하고 역산하는 값**이다 — `α = (2D−1−T)/[(D−1)(T+1)]`.

**(2) 역산 결과 0.2는 구간 안에 있다.** D=30 기준으로 목표 배율 5~10배를 넣으면
**α ∈ [0.154, 0.310]**이 나온다. 채택값 0.2가 이 구간에 들어간다.
구간을 벗어날 수 없는 이유는 양 끝이 모두 실패 모드이기 때문이다 — α=1.0이면 배율이 1.00배로
완전히 평탄해져 시간가중 차등이라는 핵심 차별점 자체가 사라지고, α=0.0이면 초반이 사실상
전액 몰수가 되어 초반 이탈자에게 "어차피 다 잃었다"는 심리를 줘 커밋먼트 장치로 역효과가 난다.

**(3) α는 총액을 바꾸지 않는다.** `Σ_{d=1..D} w(d) = stake`(망원합)이므로 **총 환급액은 α와 무관**하고,
모든 α 곡선은 `d = (D+1)/2`에서 교차한다(그 값은 `stake/D`, α 무관).
즉 α는 파이의 크기가 아니라 **교차점을 축으로 한 회전 — 시간 배분만** 조절한다.
"α를 낮추면 참가자가 손해"라는 오해를 정확히 반박하는 지점이다.

**(4) 배율은 D에 의존한다.** 같은 α=0.2에서 **D=5는 4.6배, D=30은 7.8배**다.
데모 방(D=5)의 체감 압박은 실서비스 상정(D=30)보다 약하다 — 배율을 말할 때는
반드시 어느 D 기준인지 함께 밝혀야 한다.

- 근거 스크립트: `03_시뮬레이터/alpha_sweep.py` (닫힌 형태 ↔ 실측 수열 대조 검산 포함)
- 그래프: `04_그래프/03_alpha_sweep_tradeoff.png`(트레이드오프), `04_staying_wage_by_alpha.png`(교차점)
- §4의 "α 정밀 캘리브레이션"은 종결이 아니라 **성격이 바뀌었다** — 남은 것은 설계 근거가 아니라
  실측 이탈률로 목표 배율 자체를 재조정하는 일이며, 실서비스 데이터가 있어야 가능하다

### 12.1 D-30. 프로젝트명 Locked In으로 변경

프로젝트명을 **`Locked In`**으로 확정했다 (2026-08-18, 3인 합의).
한글 병기 **갓생 내기**는 국내 청중용으로 유지한다 — 버리는 게 아니라 병기다.

| 층 | 값 | 쓰는 자리 |
|---|---|---|
| 정식 명칭 | **Locked In** | 전 문서 제목·본문 |
| 한글 병기 | **갓생 내기** | 국내 청중 대상. 제목에서는 괄호 병기 |
| 태그라인 | **Locked in. Paid out.** | README 상단, CLAUDE.md §1 |
| 기술 부제 | 시간가중 차등 몰수 습관 챌린지 프로토콜 | 제목 줄 부제 |

- **이중의미가 선택의 이유다.** "Locked in"은 집중 상태를 뜻하는 표현이면서
  동시에 **예치금이 컨트랙트에 잠긴다는 기술적 사실**이다. 밈을 모르는 사람에게도 뜻이 통하고,
  아는 사람에게는 한 겹 더 읽힌다. 이름이 메커니즘을 설명하는 쪽이므로 별도 해설이 필요 없다
- **태그라인이 프로토콜의 두 단계를 그대로 표현한다.** `Locked in`(예치) → `Paid out`(정산).
  덤으로 **구현하지 않은 층(체크인 인증, 지갑 UI)이 문장에 없어 스코프가 정직하게 드러난다** —
  이름이 D-09·D-17보다 넓은 약속을 하지 않는다
- **밈 부제는 선제적 자인이다.** 행사 주최가 자체 동아리라 캐주얼한 톤이 허용되는 자리이고,

  기술 문서 본문에는 넣지 않는다
- **기술 문서 본문의 서술 톤은 바꾸지 않는다.** 바뀌는 것은 이름 표기뿐이고,
  설계문서의 명제·증명·수치 서술은 그대로다

| 후보 | 내용 |

| **사진 인증 + AI 판정** | 참가자가 인증 사진을 올리고, AI가 판정한 결과를 오라클이 제출 |
| **낙관적 검증 + 이의제기 기간** | 제출을 일단 참으로 두고, 정해진 기간 안에 이의가 없으면 확정 |
| **외부 검증자 랜덤 배정** | 같은 방 밖의 검증자를 무작위 배정해 판정 (D-04에서 기각한 상호검증의 담합 문제를 배정 방식으로 회피) |
| **검증자 스테이킹 + 슬래싱** | 검증자가 담보를 걸고 판정하며, 오판이 드러나면 담보를 몰수 |

**이 중 하나를 고르는 것이 블록톤의 첫 결정이다.** 넷은 신뢰 가정 · 비용 · 구현량이 서로 다르고,
어느 것을 고르느냐에 따라 그 위의 설계가 전부 따라 움직인다. 다른 논의보다 이것이 먼저다.

### 13.2 어느 쪽을 고르든 컨트랙트는 바뀌지 않는다

오라클 인터페이스가 **판정 결과만** 받도록 좁혀져 있기 때문이다.

```move
public fun submit_results(ch: &mut Challenge, failed: vector<address>, ctx: &TxContext) {
    assert!(ctx.sender() == ch.oracle, ENotOracle);
    ...
}
```

컨트랙트가 아는 것은 둘뿐이다 — **누가 제출했는가**(`ch.oracle`)와 **누가 탈락했는가**(`failed: vector<address>`).
그 명단이 어떻게 만들어졌는지는 묻지 않는다. 사진을 AI가 봤든, 이의제기 기간이 조용히 지나갔든,
랜덤 배정된 검증자가 투표했든, 결과가 주소 목록 하나로 환원되는 한 컨트랙트 입장에서는 **동일한 호출**이다.

- 이것이 아키텍처 원칙 "돈은 온체인, 인증은 오프체인"(CLAUDE.md §5-1)의 실제 효용이다.
  인증 레이어 선택은 **오라클 주소 뒤에 무엇을 놓느냐**의 문제로 축소된다
- 따라서 **인증 레이어 선택은 D-27(재배포 없음)을 위협하지 않는다.** 네 후보 중 무엇을 고르더라도
  배포된 `challenge` 모듈은 그대로 쓸 수 있고, 방 ID와 `PACKAGE_ID`도 유효하다
- ⚠️ 단, **"기존 모듈이 안 바뀐다"가 "새 모듈이 필요 없다"는 뜻은 아니다.**
  검증자 스테이킹 + 슬래싱은 검증자의 담보를 다루므로 별도 컨트랙트를 요구하고,
  낙관적 검증은 이의제기 기간을 재려면 `Clock`이 필요하다 — 프로토 스코프에서 뺀 것이다(CLAUDE.md §5-6).
  바뀌지 않는 것은 정산 로직이지 시스템 전체가 아니다
