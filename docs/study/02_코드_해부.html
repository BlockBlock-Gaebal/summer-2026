Locked In · 기술 구조

코드는 실제로 어떻게 돌아가는가

앞선 해부도가 "누가 무엇을 하는가"였다면, 이 페이지는 어떤 프로그램이, 어떤 통신으로, 어떤 데이터를 주고받으며, 어떤 계산을 하는가입니다. 코드 조각은 전부 저장소에 실제로 있는 것을 그대로 가져왔고, 옆에 무슨 뜻인지 붙였습니다.

오프체인 심판 (TypeScript · Node) 온체인 (Move · Sui) 읽기 전용 (대시보드 · 조회 스크립트)
1 · 계층 구조

네 개의 층, 세 종류의 통신

에이전트는 체인에 직접 붙지 않습니다. sui client ptb라는 공식 명령줄 도구를 자식 프로세스로 띄워 "이 함수를 이 인자로 호출해 줘"라고 시키고, 서명은 CLI가 자기 키스토어로 합니다. 그래서 개인키가 코드나 .env에 없습니다.
2 · 데이터 구조

체인 위에 실제로 저장된 것

방 하나가 shared object 하나입니다. "shared"는 특정 지갑 소유가 아니라 누구나 트랜잭션에서 참조할 수 있다는 뜻이고, 여러 사람이 join해야 하니 이 형태여야 합니다. 아래는 컨트랙트의 실제 정의입니다.

public struct Challenge has key {
    id: UID,
    oracle: address,        // 탈락자 명단을 제출할 수 있는 유일한 지갑 (= 방 만든 사람)
    alpha_bp: u64,          // 환급 커브의 α. 2000 = 0.2 (basis point)
    total_days: u64,        // D = 5
    current_day: u64,       // 0에서 시작, submit_results마다 +1
    daily_drip: u64,        // 하루에 생존자에게 흘려보낼 몰수액 합계 (MIST)
    acc_per_share: u128,    // "stake 1 MIST당 누적 배당" ×1e12. 배당 계산의 핵심 지표
    vault: Balance<SUI>,    // 금고. 예치금이 전부 여기 있다
    participants: Table<address, Participant>,   // 주소 → 참가자 정보
    participant_list: vector<address>,           // Table은 순회가 안 돼서 순서 목록을 따로 둔다
    status: u8,             // 0 PENDING · 1 ACTIVE · 2 ENDED
}

public struct Participant has store {
    stake: u64,             // 건 돈 (20,000,000 MIST)
    start_day: u64,         // 참여 시작일 (시작 전 참여 = 1)
    acc_entry: u128,        // 참여 시점의 acc_per_share 스냅샷 — 내 몫 계산의 기준점
    failed_day: u64,        // 0 = 생존, n = day n에 탈락
    claimable: u64,         // 찾아갈 수 있는 금액. finalize 후 확정
}

왜 Coin이 아니라 Balance인가? Coin은 지갑 속에 낱개로 굴러다니는 "동전 객체"이고, Balance는 다른 객체 안에 품어 두는 "잔액"입니다. 금고처럼 내부에 보관할 땐 Balance가 정석입니다. join은 참가자가 준 Coin을 잔액으로 바꿔 vault에 합치고, claim은 vault에서 떼어내 다시 Coin으로 만들어 돌려줍니다.

3 · 방의 상태 변화

어떤 호출이 어떤 상태에서만 허용되는가

stateDiagram-v2
    [*] --> PENDING : create_challenge(5, 2000)
    PENDING --> PENDING : join / withdraw (철회 가능)
    PENDING --> ACTIVE : submit_results 첫 호출 (돈 잠김)
    ACTIVE --> ACTIVE : submit_results ×4 (day 2~5)
    ACTIVE --> ENDED : finalize (day == 5)
    ACTIVE --> ENDED : 생존자 0명 (전멸, 조기 종료)
    ENDED --> ENDED : claim (각자 찾아감)

컨트랙트는 각 함수 첫머리에서 assert!로 상태를 검사합니다. 조건이 틀리면 트랜잭션 전체가 abort되어 아무 일도 일어나지 않고, 에러 코드만 남습니다 (EJoinClosed, ENotOracle, EAllDaysSubmitted …). 에이전트가 dry-run으로 먼저 돌려보는 것은 이 abort를 공짜로 확인하기 위해서입니다.

4 · 핵심 함수 하나 뜯어보기

submit_results가 호출되면 컨트랙트 안에서 벌어지는 일

에이전트가 하루에 한 번 부르는 함수입니다. 인자는 방과 탈락자 주소 목록뿐. 나머지는 전부 컨트랙트가 계산합니다.

권한·상태 검사assert!(ctx.sender() == ch.oracle) · status != ENDED · current_day < total_days보낸 지갑이 오라클이 아니면 즉시 abort.
PENDING이면 ACTIVE로, 날짜 +1ch.current_day = ch.current_day + 1첫 제출 순간부터 withdraw가 막힙니다.
탈락자마다: 탈락일 기록 → 지금까지 쌓인 배당 확정 → 몰수액을 남은 날에 균등 분할해 drip에 더함p.failed_day = d · p.claimable += pending_dividend(…) · ch.daily_drip += (stake − refund) / (D − d + 1)배당은 "갱신 전 acc"로 정산해서, 그날 탈락자는 그날 배당을 못 받습니다.
오늘 생존자의 지분 합계participant_list를 돌며 failed_day == 0인 stake를 합산Table은 순회가 안 되므로 vector를 따로 들고 다니는 이유가 여기 있습니다.
생존자가 0이면 전멸 처리(ENDED), 아니면 지표 갱신acc_per_share += daily_drip × 1e12 / survivor_stake_sum개인별로 돌며 더하지 않고, 지표 하나만 올립니다 (O(1)).

acc_per_share — "개인별로 안 돌고도 정확히 나누는" 트릭

DeFi에서 흔히 쓰는 패턴(MasterChef 방식)입니다. "챌린지 시작부터 지금까지 stake 1 MIST가 받았어야 할 배당 누적치"를 하나의 숫자로 관리하고, 각자는 참여 시점의 값(acc_entry)과 정산 시점의 값의 차이 × 내 stake로 자기 몫을 구합니다. 실제 방의 숫자로 따라가면:

시점daily_drip생존자 stake 합acc_per_share 증가분누적 acc (×1e12)

B는 Day 4에 탈락하며 "갱신 전 acc" 0.132로 정산 → 20,000,000 × 0.132 = 2,640,000. A는 finalize에서 1.252로 정산 → 20,000,000 × 1.252 = 25,040,000, 여기에 원금 20,000,000을 더해 45,040,000. 체인에 실제로 기록된 값과 정확히 같습니다.

환급 공식을 정수로만 계산하는 법

Move에는 소수가 없습니다. 그래서 R(k) = α·(k/D) + (1−α)·(k/D)²를 통분해 나눗셈을 맨 마지막 한 번만 합니다.

public fun calc_refund(stake: u64, d: u64, total_days: u64, alpha_bp: u64): u64 {
    let k = if (d == 0) { 0 } else { d - 1 };          // 탈락일 d → 버틴 일수 k
    let numer = (stake as u128)
        * ((alpha_bp as u128) * (k as u128) * (total_days as u128)
            + ((10000 - alpha_bp) as u128) * (k as u128) * (k as u128));
    let denom = 10000 * (total_days as u128) * (total_days as u128);
    (numer / denom) as u64
}

C의 경우: stake 20,000,000, k = 2, D = 5, α = 2000 → 20,000,000 × (2000·2·5 + 8000·4) / (10000·25) = 20,000,000 × 52,000 / 250,000 = 4,160,000. u128로 계산하는 이유는 곱셈 중간값이 u64 한계(약 1.8×10¹⁹)에 닿기 때문입니다.

7 · 읽기 쪽

대시보드는 체인을 어떻게 읽나

Sui 공개 풀노드의 JSON-RPC가 폐지되어(설계 결정 D-23) gRPC-web으로 읽습니다. 함정이 하나 있는데, 참가자 정보가 들어 있는 Table은 Sui에서 dynamic field로 저장되어 오브젝트를 그냥 읽으면 껍데기와 개수만 나옵니다. 그래서 두 단계로 읽습니다.

Challenge 오브젝트 읽기ledgerService.getObject({ readMask: ['json'] })oracle, current_day, vault, status, participants Table의 id와 size가 나옵니다.
Table의 dynamic field ID 목록stateService.listDynamicFields({ parent: tableId })참가자 수만큼의 필드 ID. 1,000개 단위로 페이지를 넘깁니다.
필드 오브젝트 하나씩 읽기각 필드 = { name: "0x주소", value: { stake, start_day, acc_entry, failed_day, claimable } }이 로직이 scripts/read_state.ts에 있고, 대시보드도 같은 파일을 복사해 씁니다.

대시보드(frontend/src/App.tsx)는 setInterval(loadState, 5000)으로 5초마다 이 읽기를 반복합니다. 조회에 실패하면 마지막으로 성공한 화면을 유지하고 실패 횟수만 셉니다. 진행 중인 방에서는 acc_per_share로 "지금 claim하면 얼마"를 프론트에서 미리 계산해 보여 주고(dividend.ts는 컨트랙트의 pending_dividend를 연산 순서까지 똑같이 미러링), ENDED면 체인에 확정된 claimable을 그대로 씁니다.

8 · 설계 선택의 이유

심사위원이 "왜?"라고 물을 만한 것들

선택이유
개인키를 파일에 두지 않고 sui CLI로 서명키가 코드·환경변수·로그 어디에도 안 나타난다. 에이전트는 "무엇을 보낼지"만 정하고, "누구 이름으로"는 CLI 키스토어가 정한다.
돈을 컨트랙트가 보내주지 않고 각자 claim (pull 패턴)일괄 송금 루프는 참가자 수에 비례해 비싸지고 한 명 실패가 전체를 막는다. 각자 찾아가면 실패가 격리된다.
Table + vector 이중 관리Table은 O(1) 조회는 되지만 순회가 안 된다. 정산 때 전원을 돌아야 하므로 주소 목록을 따로 든다.
acc_per_share 지표 하나로 배당매일 참가자 전원을 돌며 더하면 O(n). 지표 하나만 올리면 O(1)이고, 중도 참여자의 "진입 전 배당 제외"가 뺄셈으로 자동 보장된다.
나눗셈은 마지막 한 번, u128 누적정수 연산의 절단 오차를 최소화. 실측 dust 0의 배경.
LLM 출력을 JSON 스키마로 강제 + 파싱 실패는 에러판정이 온체인 집행으로 이어지므로 "애매하면 FAIL"이 아니라 "애매하면 멈춤"이어야 한다.
기억을 로컬이 아니라 Walrus에판정 근거가 에이전트 밖에, 공개 검증 가능한 곳에 남는다. blobId 하나로 누구나 같은 기억을 재생할 수 있다 (replay.ts).
gRPC로 읽기공개 풀노드의 JSON-RPC가 2026-08에 폐지됐다. 선택이 아니라 필수.
