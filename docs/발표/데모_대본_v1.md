## 0. 전제 — 무대에서는 절대 create_challenge/join을 안 한다 (D-18)

방 생성·참가자 등록은 **리허설 때 미리 끝내둔다.** 발표 당일에는 `submit.ts`만 무대에서
누른다. 근거: 무대에서 다수 지갑 서명은 실패 리스크가 크고, 부수 효과로 "빈 방에
submit_results 호출 → 전멸 오판정" 사고(D-22)도 원천 차단된다.

**발표 전날 할 일 (1회):**

```bash
cd scripts
npm run seed        # A(유안=오라클) 자동 join. B/C 주소가 .env에 있으면 안내 커맨드 출력
```

B/C는 `seed.ts`가 대신 서명해주지 않는다 (각자 실제 서명 주소가 필요 — 회의 결정,
CLAUDE.md §5-3 "돈은 온체인, 인증은 오프체인"과 별개로 join 자체는 각자 서명 필수).
`seed.ts` 출력에 찍히는 `sui client ptb ...` 명령을 B/C 계정으로 직접 실행해 참여를
완료해둔다. `npm run read-state -- <방ID>`로 **참가자 3명, 상태 PENDING**을 확인하고
무대 전날 준비를 마친다.

## 1. 시나리오 (고정값 — `submit.ts`의 `SCHEDULE`와 반드시 일치)

| day | 사건 | 근거 |
|---|---|---|
| 1 | B 탈락 | — |
| 2 | 없음 | — |
| 3 | C 탈락 | — |
| 4 | 없음 | — |
| 5 | A 완주 (submit 5회 후 자동 finalize) | `submit.ts`가 5일째 제출 직후 `finalize()`까지 자동 호출 |

> ⚠️ `발표구성안.md` S5의 예전 표(B가 day2, C가 day4, stake 10 SUI)는 **이 문서가
> 최신값으로 대체한다.** 아래 표는 2026-08-15에 데모 방(`DEPLOYMENT.md` 방③,
> `0x2f6f1b32...`)에서 이 시나리오 그대로 5일 + finalize까지 실제로 돌려서 나온
> **테스트넷 실측값**이다 (stake는 검증용 0.02 SUI 기준 — 비율은 발표용 10 SUI와
> 동일하다). 진모가 파이썬 미러로 별도 계산해 **완전히 일치함을 확인했다** —
> 이 값이 정본이다.

| | 예치 | 탈락 | 커브 환급 | 생존 배당 | **최종 수령** |
|---|---|---|---|---|---|
| A | 0.02 | 완주 | 0.02 (원금 전액) | 0.03184 | **0.05184 SUI** |
| B | 0.02 | day1 | 0 | 0 | **0 SUI** |
| C | 0.02 | day3 | 0.00416 | 0.00400 | **0.00816 SUI** |
| 합계 | 0.06 | | | | **0.06 SUI** (dust 0) |

**C의 분해가 발표의 핵심이다.** C는 중간에 탈락했는데도 0.00816을 받는다. 그중
절반(0.004)은 살아있던 day1~3 동안 B의 몰수분에서 흘러들어온 배당이다 — "탈락해도
버틴 기간의 몫은 가져간다"는 우리 차별점이 숫자 한 줄로 증명되는 지점이다. 반면
B는 day1 탈락이라 완주일수 k=0 → 환급 0 → 배당도 0 → 전액 몰수. 같은 "탈락"인데
결과가 완전히 다르다 — 이 대비가 킬러 슬라이드다.

**발표 슬라이드용 (stake 10 SUI 기준, ×500 스케일):**

| 참가자 | 최종 수령 (SUI) |
|---|---|
| A | 25.92 |
| B | 0.00 |
| C | 4.08 |
| 합 | 30.00 (보존 ✓) |

재검증 필요하면
`npm run seed` + `npm run submit` ×5를 다시 돌리면 된다 (재현 가능, 매번 같은
시나리오·같은 결과 나옴).

## 2. 큐시트 (S5→S6, 약 100초)

| 순서 | 화면 | 대사 | 명령/클릭 |
|---|---|---|---|
| 1 | 대시보드, PENDING 상태, 참가자 3명 | "지금 이 방은 어젯밤 미리 만들어둔 실제 테스트넷 방입니다. A·B·C 세 명이 각자 서명해서 참여했습니다" | (사전 세팅 결과 보여주기만) |
| 2 | 터미널 | "오라클 스크립트로 하루씩 진행시켜 보겠습니다. day1엔 B가 탈락하는 시나리오입니다" | `npm run submit` |
| 3 | 대시보드 새로고침 | "B가 day1 탈락으로 표시되고, 환급 0원 — 저희 커브 설계의 의도된 지점입니다" | 대시보드 폴링(5초) 대기 또는 수동 새로고침 |
| 4 | 터미널 | "day2는 아무도 안 빠집니다. 탈락자가 없는 날도 반드시 빈 명단으로 호출해야 진행됩니다" | `npm run submit` |
| 5 | 터미널 | "day3, C 탈락" | `npm run submit` |
| 6 | 대시보드 | "B와 C 수령액이 다릅니다 — 같은 탈락인데 시점에 따라 갈립니다. 이게 저희 차별점입니다" | (S5 멘트 재사용) |
| 7 | 터미널 ×2 | "day4, day5 진행하면 A가 완주하고 자동으로 정산이 마감됩니다" | `npm run submit` (×2, 5번째 호출에서 finalize 자동 실행) |
| 8 | 대시보드 | "ENDED, A는 원금 전액 + 배당까지 받습니다. 합계를 보면 새거나 사라진 돈이 없습니다" | `npm run read-state -- <방ID>` (백업 경로) |

시간이 빠듯하면 4단계(day2)를 건너뛰고 미리 "day2는 방금 무대 밖에서 눌러뒀다"고
말하며 3→5로 넘어가도 된다 — `submit.ts`는 체인의 `current_day`를 직접 읽어 다음
날짜를 스스로 판단하므로 발표 중 몇 번을 누르든 순서만 맞으면 안전하다.

## 3. 백업 플랜 (D-16)

- **대시보드가 안 뜨면**: `npm run read-state -- <방ID>`로 터미널에서 동일한 정보(참가자별
  stake/failed_day/claimable, vault, status)를 보여준다. 표 포맷이 이미 사람이 읽기
  좋게 정리돼 있다.
- **RPC가 아예 안 되면**: 리허설 때 위 큐시트 진행 과정을 화면 녹화해둔다. 라이브
  실패 시 즉시 녹화본으로 전환한다는 것만 발표자와 미리 합을 맞춘다.
- **오라클 키가 있는 노트북이 아니면**: `submit.ts`는 `ORACLE_PRIVATE_KEY`가 있는
  기기에서만 실행 가능하다. 발표 노트북에 미리 `.env` 세팅이 돼 있는지 리허설 때
  반드시 확인한다 (`.env`는 gitignore 대상이라 클론만으로는 안 딸려온다).
